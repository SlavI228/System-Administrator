Project 7 — Backup & Disaster Recovery

Status: Advanced Lab Project Environment: AcmeLab virtual infrastructure

Executive Summary

Project 7 establishes a backup and disaster-recovery capability for the AcmeLab lab environment. The design introduces a dedicated BACKUP01 server, structured backup storage, automated Linux file backups, restore verification, retention planning, RPO/RTO definitions, and disaster-recovery runbooks. The project emphasizes a critical operational principle: a backup is not proven until it has been successfully restored and verified.

Objectives

• Design a practical 3-2-1-style backup strategy. • Define recovery point objectives (RPO) and recovery time objectives (RTO). • Deploy BACKUP01 as a dedicated backup repository. • Back up FILE01 data using rsync and dated backup generations. • Automate and log backup execution. • Test restoration of deleted files and directories. • Validate restored data using checksums. • Simulate server loss and document recovery procedures. • Protect backups through access control, separation, and offline/secondary copies.

Target Architecture

The target design separates production systems from backup storage and provides a secondary or offline copy. In the lab, the architecture is:

Backup Strategy

The recommended lab strategy follows the 3-2-1 principle: maintain at least three copies of important data, use two different storage locations or media, and keep one copy separated from the normal production environment. A simple rsync mirror is not sufficient by itself because deletion or corruption at the source can propagate to a mirror.

Copy Location Purpose

Primary FILE01 Active production data

Backup BACKUP01 Operational recovery

Secondary External separate repository Protection against backup-server or ransomware-style failure

RPO / RTO

RPO defines the maximum acceptable amount of data loss. RTO defines the target time to restore service. The following are project targets for the lab and should be adjusted for a real organization.

Backup Implementation

BACKUP01 is configured as a dedicated Ubuntu Server backup repository. A dedicated storage volume for /backup is preferred.

Backup structure:

/backup/ ├── 2026-09-04/ ├── 2026-09-05/ ├── 2026-09-06/ └── latest/

FILE01 company data is collected into dated backup generations. Dated generations reduce the risk that a single accidental deletion immediately destroys the only recoverable copy.

Automation & Logging

The backup process should be executed by a controlled script and scheduled through cron or an equivalent scheduler. The script must return a failure exit code when rsync fails and should write execution results to a dedicated log.

Recommended flow:

Connectivity check → destination creation → backup → exit-status check → verification → logging → retention.

Restore Testing

A controlled restore test should delete a harmless test file from FILE01, restore it from a dated backup, and verify both its presence and content. SHA-256 checksums can be used to demonstrate that the restored content matches the backup copy.

Disaster Recovery Scenario

Scenario: FILE01 becomes unavailable because of a simulated disk or server failure. The recovery process should provision a replacement Linux server, reinstall required services, restore the most recent valid backup, verify permissions and service operation, reconnect monitoring, and document the incident.

Recovery sequence:

1. Identify the incident.

2. Determine scope and protect remaining systems.

3. Identify the latest valid backup.

4. Verify backup integrity.

5. Prepare replacement server.

6. Restore data and configuration.

7. Restore services and permissions.

8. Validate application/file access.

9. Re-enable monitoring and backups.

10. Record actual RPO/RTO and complete the post-incident review.

Security Controls

• Restrict access to backup storage using least privilege. • Use individual administrative accounts rather than routine root access. • Use SSH keys for automated Linux administration where appropriate. • Protect backup credentials and never commit secrets to Git. • Encrypt backup data when required by

the environment or data sensitivity. • Maintain a secondary/offline copy that is not continuously exposed to production credentials. • Monitor backup failures and review backup logs.

Final Assessment

Project 7 moves the AcmeLab environment from simple server administration toward resilient infrastructure operations. The strongest outcome is not the presence of a backup directory; it is the ability to demonstrate a repeatable, documented, and tested recovery process.
